# Belal — دليل العمل مع الذكاء الاصطناعي لتطوير المشاريع

الإصدار: 1.0 — 12 أكتوبر 2026  
الحالة: مرجع أولي قابل للمراجعة؛ هيكل الحفظ والمهارات أدناه مقترح، ولم يُثبّت على جهاز المستخدم.  
المالك: Belal Alswerki

## 1. الغرض وحدود هذا المرجع

حفظ طريقة بلال في التفكير والتنفيذ والتصميم والتسليم، بحيث يبدأ أي مشروع جديد بسياق واضح وتوقعات عملية. يفصل الدليل بين التفضيلات الشخصية، والقرارات الخاصة بكل مشروع، والأدوات التي تُختار بحسب الحاجة.

النسخة الأولى مبنية أساساً على سياق SetOdoo المتاح وتصحيحات بلال المباشرة، مع أمثلة إصدار متاحة من Hablero وTeorico España. لم تتوفر مراجعة كاملة وموثوقة لكل تفاصيل محادثتي التطبيقين، وبعض نتائج الاسترجاع خلطت مشاريع مختلفة؛ لذلك لا تُنسب إليهما هنا تقنيات أو تفضيلات غير مؤكدة. يمكن استكمال ملخصيهما من مستودعيهما وملاحظاتهما المعتمدة لاحقاً.

وجود أداة في هذا الدليل لا يثبت أنها مثبتة في جهاز أو مشروع جديد. وجود تفويض نشر في مشروع سابق لا يمنح التفويض لمشروع آخر.

## 2. التفضيلات الشخصية المؤكدة

- ابدأ من هدف العمل والمستخدم: ما المشكلة التي نحلها، وما النتيجة التي تجعل المشروع مفيداً وقابلاً للعرض والتسويق؟
- قدّم أفكاراً محددة وسيناريو واضحاً، ثم اترك للمنفّذ مجالاً لتحسين التفاصيل والإبداع.
- أنجز المهمة إلى نتيجة يمكن تشغيلها وتجربتها ومراجعتها؛ اربط العمل التقني بالنتيجة العملية.
- التصميم مهم: هوية متناسقة، ألوان جميلة، رسوم توضيحية، أيقونات مناسبة، وتجربة تنقّل يشعر فيها المستخدم بتغيّر الصفحة.
- بساطة مع شخصية واضحة: اضبط كثافة المحتوى والمساحات؛ تجنّب الفراغ الزائد الذي يجعل الصفحات متشابهة أو ضعيفة.
- استخدم الحركة لتفسير العمل وتحسين التفاعل. حافظ على ظهور المحتوى المهم فوراً وسهولة استخدام الهاتف.
- سهولة إدارة المحتوى جزء من جودة المشروع؛ لوحة الإدارة تحتاج تسميات واضحة وتنظيماً يخدم الموظف الفعلي.
- نفّذ باستقلالية داخل نطاق التفويض. حلّ التفاصيل الروتينية دون طلب تأكيد متكرر، واسأل عن القرارات التي تتطلب معلومة أو تفويضاً فعلياً.
- راجع الواجهة بصرياً وجرّب المسارات الفعلية؛ الاختبارات الآلية تدعم الحكم على الجودة.
- احفظ العمل في Git وقدّم تقريراً موجزاً وواضحاً: ما تغيّر، وما اختُبر، وأين تُجرّب النتيجة، وما الذي بقي.
- لا تختلق نتائج أو أرقاماً أو اعتماداً تجارياً. فرّق بين القياسات المحلية والحالة الحقيقية في الإنتاج.
- التواصل مع بلال بالعربية الواضحة مع الشرح. لغة المنتج والسوق تُحدّد في سياق المشروع.

## 3. التنظيم المقترح: مصدر واحد مع نسخ استخدام واضحة

أنشئ مستودعاً خاصاً مقترح الاسم: `belal-development-playbook`. يحتوي:

| الملف المقترح | وظيفته |
| --- | --- |
| `PROFILE.md` | التفضيلات الشخصية المؤكدة، مع مصدر كل تعديل مهم |
| `TOOLS.md` | الأدوات المفضّلة، ومتى تُستخدم ومتى لا تناسب |
| `WORKFLOW.md` | خطوات العمل ومعيار التسليم |
| `CHANGELOG.md` | تاريخ التغييرات التي أقرّها بلال |
| `adapters/claude/CLAUDE.md` | نسخة مختصرة من التفضيلات لتحميلها في Claude Code |
| `templates/PROJECT_CONTEXT.md` | قالب تعريف أي مشروع جديد |
| `templates/PROJECT_STATE.md` | قالب متابعة الحالة الفعلية |
| `examples/setodoo.md` | مثال معتمد من مشروع SetOdoo |
| `examples/hablero.md` و`examples/teorico.md` | ملخصات تُستكمل من مصادر المشروعين |
| `skills/` | إجراءات قابلة للاستدعاء، تُبنى لاحقاً إذا احتاجها الاستخدام |

ابدأ بالملفات الأساسية دون سكربتات أو خادم ذاكرة إضافي. يتولى Git حفظ النسخ والتعديلات. سجّل في كل مشروع إصدار الدليل الذي اعتمده، ثم طبّق التحديثات عليه بوضوح؛ لا تغيّر سلوك جميع المشاريع تلقائياً من تعديل غير مراجع.

على جهاز بلال، توضع النسخة المختصرة في `~/.claude/CLAUDE.md` بعد دمجها مع التعليمات الموجودة وحفظ نسخة منها. تبقى ملفات الدليل التفصيلية مرجعاً يُقرأ عند الحاجة. لا تستبدل الإعدادات الحالية أو تعليمات المشروع عشوائياً.

في جلسة ChatGPT جديدة، أرفق المرجع أو الملخص المناسب واطلب استخدامه. لا يُفترض أن رفع الملف مرة واحدة يجعله محمّلاً تلقائياً في كل محادثة.

## 4. نسخة مختصرة مقترحة للتعليمات الشخصية

النص التالي قابل للنقل إلى ملف تعليمات Claude الشخصي بعد المراجعة والدمج:

```markdown
# Belal — Personal development preferences

Apply these preferences together with the current project's instructions.
Project-specific constraints and the user's latest explicit instructions govern
the work. This profile grants no additional deployment or release permissions.

- Communicate with Belal in clear Arabic; explain decisions briefly.
- Establish the business goal, target user, and acceptance criteria first.
- Inspect the current repository and working behavior before changing them.
- Complete the requested work through implementation and appropriate validation.
- Work autonomously within the authorization already given for this project.
- Ask only for missing information or authorization that materially blocks work.
- Aim for polished, colorful, coherent design with meaningful visuals and motion.
- Design mobile intentionally; make navigation and page changes clear.
- Keep content readable immediately; respect reduced motion and accessibility.
- Make administration clear and useful for the people who will operate it.
- Select tools for the task; use the existing approved stack when appropriate.
- Treat GSAP, Lenis, React Bits, Council, and Brag as available preferences to
  evaluate, not mandatory dependencies for every project or screen.
- Visually inspect meaningful UI changes and verify important real user flows.
- Run relevant checks; stop repeating them once the agreed gate is satisfied.
- Keep concurrent work isolated and preserve other sessions' changes.
- Never invent business facts, metrics, certificates, testimonials, or test results.
- Keep secrets and real private data out of prompts, screenshots, and Git.
- Report what changed, validation, access links, commit, and actual release state.
- Preserve these preferences separately from each project's architecture,
  language, credentials, brand, and publication rules.
```

## 5. سجل الأدوات الأولي

هذه قائمة تفضيلات وأدوات مستخدمة أو مطلوبة في سياق SetOdoo، وليست قائمة تثبيت إلزامية.

| الأداة | موقعها في طريقة العمل | الاستخدام المناسب وحدود الاختيار |
| --- | --- | --- |
| ChatGPT | التفكير والتحليل وصياغة المتطلبات | ترتيب الأولويات، مراجعة التقارير، إعداد اتجاه واضح قابل للتنفيذ |
| Claude Code Desktop | التنفيذ | فحص المشروع، تعديل الملفات، تشغيله والتحقق منه والتسليم ضمن التفويض |
| GSAP | مفضّلة للحركة على الويب | المشاهد والرسوم والتفاعلات التي تستفيد من تسلسل مضبوط؛ لا تؤخر النص الأساسي |
| Lenis | مفضّلة عند وجود فائدة واضحة | تقييم التمرير السلس في الموقع العام؛ ليس إلزامياً في الإدارة أو النماذج أو التطبيقات الأصلية |
| React Bits | مفضّلة لمكونات الويب الإبداعية | انتقاء مكونات تخدم الهوية وتجربة الاستخدام؛ توافق الإطار والأداء والترخيص شرط للاختيار |
| claude-council | أداة مراجعة مستخدمة | نقد البدائل أو واجهة ذات قرار مهم؛ تحدّد طريقة التشغيل والمواد المشاركة لكل مشروع |
| Brag | أداة إنتاج تسويقي مستخدمة | فيديو إطلاق مبني على المنتج والهوية، مع صوت ونص وحقوق أصول موثقة |
| Playwright وأدوات اختبار الإطار | تحقق مستخدم في SetOdoo | اختيار أداة مناسبة للويب أو التطبيق؛ أعداد الاختبارات السابقة ليست هدفاً ثابتاً |
| Git وGitHub | حفظ العمل وتسليمه | فروع ومراجعات ونسخ واضحة؛ سياسة الدمج والتوزيع خاصة بكل مشروع |
| Three.js | خيار اقترحه بلال عند الحاجة | ما زال اختياراً مشروطاً؛ يُستخدم حين يضيف عرض 3D قيمة ملموسة للتجربة |

التقنيات المستخدمة في SetOdoo، مثل Python وDjango وSQLite وReact وTypeScript وReact Router وTailwind، تُحفظ كاختيارات لذلك المشروع. لا يُفرض استعمالها على مشروع iOS أو موقع بسيط أو منتج مختلف.

لكل أداة يضاف لاحقاً: المصدر الرسمي، سبب الاختيار، بيئة التثبيت، الإصدار الفعلي، تاريخ التحقق، الترخيص، تكلفة التشغيل، وطبيعة البيانات التي تصل إليها. قيّم تحديثها عند الحاجة للمشروع ولا تثبّت أحدث إصدار تلقائياً.

## 6. دورة العمل المقترحة

1. **فهم المهمة:** هدف تجاري واضح، مستخدم، سيناريو استعمال، ومخرجات القبول.
2. **فحص الواقع:** الكود، الخوادم، البيانات، ما يعمل حالياً، وأي جلسات متزامنة.
3. **اختيار الاتجاه:** تصور محدد للتصميم والتنفيذ. البدائل مفيدة عند وجود قرار مؤثر؛ لا تكرر مرحلة المقترحات لكل تعديل صغير.
4. **تنفيذ قابل للمراجعة:** فرع أو worktree مناسب، نطاق واضح، وتحديثات عربية قصيرة عند النتائج المهمة.
5. **تحقق مناسب:** فحوص تقنية، مراجعة بصرية، وتجربة أهم المسارات والأدوار والحالات.
6. **تسليم:** ملفات المصدر، commit، دليل تشغيل مختصر، وروابط أو ملفات قابلة للاستخدام.
7. **إصدار داخل التفويض:** نشر أو بناء أو رفع أو تقديم مراجعة حسب سياسة المشروع، ثم قراءة الحالة الفعلية والتحقق منها.
8. **حفظ التعلم:** دوّن التصحيح العام في الملف الشخصي، والقرار المحلي في المشروع، بعد التأكد من نطاقه.

لا تتوقف عند خطة أو تقرير إذا كانت المهمة تشمل التنفيذ. ولا تستمر في تحسينات لا نهائية بعد اكتمال معيار القبول؛ انتقل إلى تجربة بلال والنتيجة التجارية التالية.

## 8. معيار القبول حسب نوع العمل

| نوع العمل | النتيجة التي تساعد بلال على المراجعة |
| --- | --- |
| صفحة أو واجهة ويب | رابط يعمل، فحص الهاتف والحاسوب، لقطات للعرض عند طلبها، تنقّل واضح، حالات تحميل وخطأ وفراغ مناسبة |
| إدارة أو CMS | صلاحيات فعلية، محتوى مفهوم، مسودة ومعاينة ونشر حيث يتطلب المشروع، ومسارات سهلة للموظف |
| تطبيق محمول | البناء الصحيح واختبار المسارات الأساسية والجهاز المناسب؛ حالة التوزيع والمتجر مقروءة بوضوح |
| إصدار إنتاج | commit المنشور، نجاح التشغيل، سلامة البيانات، وفحوص ذات صلة بالمهمة |
| مادة تسويقية | ملفات فعلية قابلة للتنزيل، رسالة مفهومة، هوية صحيحة، مصدر قابل لإعادة الإنتاج، وحقوق موثقة |

في التطبيقات، ميّز بين إعداد البناء، ورفعه، وتوزيعه داخلياً، وتقديمه للمراجعة، وإطلاقه للعامة. تقارير Hablero وTeorico المتاحة تُظهر أهمية معرفة المرحلة الفعلية؛ لا يجوز اعتبار الرفع دليلاً على قبول المتجر أو الإطلاق.

## 9. مهارات مقترحة لاحقاً

هذه أسماء وإجراءات مقترحة، وليست أوامر مثبتة حالياً:

- **belal-project-start:** يقرأ الملف الشخصي، يفحص المشروع، ويجهّز سياقه ومعيار القبول.
- **belal-ui-review:** يراجع شاشة فعلية، كثافة المحتوى، الحركة، التنقّل، الهاتف، والإدارة إذا كانت ضمن المهمة.
- **belal-release-check:** يراجع الجاهزية والتفويض والحالة، ويطبّق مسار الإصدار المطلوب دون اختراع إذن نشر.
- **belal-project-close:** يجهّز التسليم ويحدّث الحالة والقرارات ويسجل الدروس التي يمكن تعميمها.

تُكتب المهارات في SKILL.md عند تنفيذ هذه المرحلة فعلياً. التفضيلات القصيرة تبقى في التعليمات الدائمة؛ الإجراءات الطويلة تُحمّل عند الحاجة. يراجع المنفّذ بيئة Claude: محلية أو SSH أو سحابية، لأن نطاق التحميل يختلف.

## 10. قاعدة تحديث المعرفة

- **مؤكد:** طلب أو تصحيح صريح من بلال؛ احتفظ بالنص المختصر ومصدره وتاريخه.
- **خاص بالمشروع:** قرار لغة أو قاعدة بيانات أو علامة أو إصدار أو صلاحيات.
- **مقترح:** فكرة من ChatGPT أو المنفّذ؛ لا تحولها تلقائياً إلى تفضيل شخصي.
- **تجريبي:** أداة جُرّبت ولم يعتمد بلال نتيجتها بعد.
- **معتمد:** أكّد بلال النتيجة بعد التجربة؛ مثال: لوحة إدارة SetOdoo في 12 أكتوبر 2026.
- **مستبدل:** قرار أحدث؛ احتفظ به في سجل التغييرات دون استمرار تحميله كقاعدة نشطة.

عند نهاية مرحلة مهمة، يكفي تسجيل تعديل صغير واضح إذا ظهرت معلومة جديدة. لا تُحوّل كل محادثة إلى ملف طويل أو تعليمات دائمة.

## 11. رسالة البدء في مشروع جديد

> استخدم دليل عملي Belal Development Playbook بالإصدار المعتمد. افحص هذا المشروع أولاً، وحدّد هدفه ومستخدميه وسياقه ومعيار قبول المهمة. طبّق تفضيلاتي في التصميم والتنفيذ والتسليم، واختر الأدوات المناسبة له. احفظ القرارات الخاصة به في PROJECT_CONTEXT.md، واتبع التفويض الموجود فيه وفي رسائلي. المهمة الحالية هي: [وصف المهمة]. أكمل العمل إلى نتيجة قابلة للتجربة، مع تحديثات عربية مختصرة.
